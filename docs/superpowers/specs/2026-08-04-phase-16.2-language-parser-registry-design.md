# Phase 16.2 — Language parser registry (design)

Date: 2026-08-04
Status: **proposed**
Target release: **3.11.0**

## Scope

This delivers the remaining deferred item from Phase 16: language-specific
dependency parsers behind a stable contract. Phase 16.1 built the exclusion
policy, but its enforcement surface is JS/TS only, because the dependency graph
and the context compiler are both hard-wired to the JS/TS (Babel) analyzer. This
phase introduces an extension-keyed parser registry, routes **both the graph and
the compiler** through it, and adds a **line-based Python parser** as the proof
language with real declaration spans (full bodies) and both relative and
repo-root absolute import resolution.

**In scope:**

- An extension-keyed parser registry (`LanguageParser` interface) with a
  discriminated `ImportResolution` result.
- Refactor `dependency-graph.ts` to consume the registry.
- Route every `analyzeSource` call site in `context-compiler.ts` through the
  registry so compaction/expansion never feed Python to Babel.
- Wrap the existing `analyzeSource` (Babel) as `typescriptParser`, unchanged.
- A line-based `pythonParser`: node extraction with real declaration spans
  (decorators + full body), export/test heuristics, and relative + repo-root
  absolute import resolution.
- Additive `language` field on dependency-graph nodes; Python Markdown fences.
- Graph-level ignore of `.venv` and `__pycache__` for inventory safety.
- Activation of Phase 16.1 exclusion enforcement for `.py`/`.pyi` files.

**Out of scope (deferred):**

- Go and Rust parsers (Phase 16.2b / 16.2c), which register against the same
  contract.
- Python `src`-layout resolution, `sys.path` resolution, and namespace packages.
  Absolute imports are resolved only against the repository root; anything not
  found there is external.
- Re-export lineage across Python modules.
- AST-based Python parsing (tree-sitter or equivalent). No new runtime dependency.
- Profile-gated parser activation. Parsers are keyed by file extension.

## Decisions

1. **The registry is keyed by file extension, not by profile.** A Python file is
   Python regardless of the manifest profile; profile-specific filtering is
   already handled by the Phase 16.1 exclusion policy. Deliberate simplification
   of the original ROADMAP wording ("profiles register parsers").
2. **The JS/TS analyzer is wrapped, not rewritten.** `analyzeSource` stays in
   `source-analysis.ts`; a thin `typescriptParser` implements the contract over
   it. A golden-fixture regression test asserts JS/TS graphs are unchanged.
3. **Python parsing is line-based with real spans.** No new dependency. Node
   extraction produces full declaration spans (decorators through body) so the
   compiler can slice complete functions/classes. Relative and repo-root absolute
   imports produce edges; unresolved absolute imports are external.
4. **The graph schema stays `schema_version: 1`.** The new `language` node field
   is additive; legacy nodes omitting it remain valid and are treated as
   `typescript`.
5. **Phase 16.1 exclusion-policy logic is not modified, but compiler/expansion
   parsing dispatch must be routed through the registry.** Enforcement activates
   because Python nodes now exist for `matchExclusion` to match on; separately,
   every source-parsing call site (graph and compiler) must select a parser by
   file extension rather than calling Babel directly.
6. **Import classification lives in the parser via a discriminated result.**
   `resolveImport` returns `{ status: 'resolved', path } | { status: 'external' }
   | { status: 'unresolved_local' }`. Graph assembly maps these onto the existing
   `reason` set and handles `dynamic_expression` (missing specifier) itself. No
   per-language `switch` in graph assembly, so adding Go/Rust needs no graph edit.

## Architecture

```text
bin/lib/language-registry.ts   NEW: LanguageParser + ImportResolution contract;
                                    extension-keyed registry with fail-fast
                                    collision checks; static registration
bin/lib/source-analysis.ts     EDIT: add a typescriptParser export wrapping
                                    analyzeSource (file NOT renamed, to avoid
                                    churn across its many importers)
bin/lib/python-analysis.ts     NEW: pythonParser (line-based, real spans)
bin/lib/dependency-graph.ts    EDIT: consume the registry; language node field;
                                    parser-driven import classification; ignore
                                    .venv/__pycache__
bin/lib/context-compiler.ts    EDIT: route all analyzeSource call sites through
                                    the registry; add Python Markdown fence
bin/lib/types.ts               EDIT: add optional `language` to DependencyGraphNode
```

The parser modules stay free of process/manifest access. `dependency-graph.ts`
remains the only filesystem/graph-assembly surface.

### LanguageParser interface

```ts
// language-registry.ts
import type { SourceAnalysis } from './source-analysis.js';

export type ImportResolution =
  | { status: 'resolved'; path: string }
  | { status: 'external' }
  | { status: 'unresolved_local' };

export type ImportResolutionContext = {
  sourceFiles: ReadonlySet<string>; // all indexed files, repo-relative POSIX
};

export type LanguageParser = {
  id: string;                    // 'typescript' | 'python'
  extensions: readonly string[]; // ['.ts', ...] | ['.py', '.pyi']; each '.'+lowercase
  /** Extract imports/exports/declarations from one file. Pure, no I/O. */
  analyze(content: string, file: string): SourceAnalysis;
  /** Classify + resolve one import specifier. Pure. */
  resolveImport(importer: string, specifier: string, context: ImportResolutionContext): ImportResolution;
};

export type LanguageParserRegistry = {
  register(parser: LanguageParser): void;
  parserForFile(file: string): LanguageParser | null;
  allExtensions(): string[];
};

/** Isolated registry for unit tests and future static composition. */
export function createLanguageRegistry(parsers?: readonly LanguageParser[]): LanguageParserRegistry;

/** Helpers backed by the statically populated production registry. */
export function parserForFile(file: string): LanguageParser | null; // by path.extname
export function allExtensions(): string[];                          // sorted union
```

### Registry hygiene (fail-fast, deterministic)

- **Static production registration only.** `typescriptParser` and
  `pythonParser` populate the production registry at module import time; command
  code cannot mutate it. `createLanguageRegistry` provides an isolated registry
  so collision tests do not mutate global process state.
- **Duplicate parser `id`** → registry construction/registration throws.
- **Two parsers claiming the same extension** → construction/registration throws
  (fail-fast, no silent last-writer-wins).
- **Extension format** is validated on registration: each must start with `.`,
  be lowercase, and the union returned by `allExtensions()` is sorted and unique.
- **`parserForFile`** matches by `path.extname(file)` (lowercased); returns
  `null` for unknown extensions. Since the inventory is built from
  `allExtensions()`, every inventory file has a parser; graph assembly still
  guards against `null` defensively.

`SourceAnalysis` is reused verbatim, so `context-compiler.ts` and every
downstream consumer stay language-agnostic.

## Data model — graph schema

```ts
export type DependencyGraphNode = {
  id: string;
  path: string;
  hash: string;
  exports: string[];
  declarations?: string[];
  language?: string;   // NEW: 'typescript' | 'python'; absent = legacy (treat as 'typescript')
};
```

- `language` is set from `parser.id` at build time. Additive; `schema_version`
  stays `1`.
- `settings.extensions` now reflects `allExtensions()` (includes `.py`, `.pyi`).

### Validation (`isDependencyGraph`)

- Accept absence of `language` (legacy graph stays valid).
- When present, require a trimmed, non-empty string. Do **not** require it to be a
  registered id (graphs from a different CLI build must not be rejected).
- Edge kinds stay `{static_import, dynamic_import, require}`. Python imports reuse
  `static_import`; no new kind.

## Compatibility and staleness

- Running `--refresh-codegraph` with the new CLI on a repo containing `.py` files
  indexes them for the first time: node count grows and `fingerprint` changes.
- Consequence: `checkDependencyGraphHealth` reports **`stale`** once for any
  Python-containing repo that previously generated a graph with an older CLI.
  Desired — the `stale` message already instructs `--refresh-codegraph`. No
  migration needed.
- Pure JS/TS repos: with no Python files present, inventory and fingerprint do
  not change, so an existing graph stays `ok`. `settings.extensions` does not
  participate in the fingerprint (`buildSourceInventory` hashes only file
  contents), so this is safe even though the extension set grew.
- Adding `.venv`/`__pycache__` to ignored directories changes the inventory only
  for repos that previously indexed such files — which JS/TS-only inventories
  never did, so no regression there.

## Preserved JS/TS behavior (must not change)

- `.d.ts` files are still excluded from indexing (the existing check in
  `dependency-graph.ts` `isSourceFile`).
- `typescriptParser.resolveImport` preserves the current candidate order:
  extension probing, `index.*` fallback, and `.js` specifiers resolving to `.ts`.
- The TypeScript resolver probes **only** JS/TS extensions, so `./foo` never
  resolves to `foo.py`. The Python resolver probes only `.py`/`.pyi`. No
  cross-language edge is ever created just because `sourceFiles` contains both
  languages.
- The golden-fixture regression test (below) enforces structurally identical
  JS/TS nodes, edges, and unresolved entries after normalizing additive/dynamic
  fields.

## Python parser semantics (`python-analysis.ts`)

Line-based scanning that tracks indentation, `#` comments, and triple-quoted
string state. Considers **column 0 (top-level)** for declarations/exports.
Returns the standard `SourceAnalysis` with JavaScript string offsets (UTF-16
code-unit indices), matching the Babel analyzer's slicing contract.

**Extensions:** `.py`, `.pyi`.

### Declarations, spans, and signatures

A top-level declaration is a column-0 `def` / `async def` / `class`, optionally
preceded by a contiguous block of column-0 decorator logical statements
(`@...`). A parenthesized multi-line decorator is tracked through balanced
brackets and belongs to the same declaration span.

- **`start`** = UTF-16 code-unit offset of the first decorator line if the declaration has a
  contiguous column-0 decorator block; otherwise the `def`/`class` keyword line.
- **`end`** = UTF-16 code-unit offset just before the next top-level construct begins (the
  next column-0 line that starts a new `def`/`class`/`@decorator`/statement),
  with trailing blank lines trimmed; end-of-file if none follows. The **full
  body is included** in the span, so the compiler's full-excerpt mode slices a
  complete function/class.
- **`signature`** = the header text from the `def`/`class` keyword **through the
  suite colon that ends the header** (the first `:` at bracket depth 0),
  exclusive of any inline body after it, **preserving newlines**. So
  `def g(): return 1` → `def g():` and `def f() -> int: ...` → `def f() -> int:`.
  Multi-line signatures are **supported**; colons inside parameter annotations or
  defaults (e.g. `x: dict = {1: 2}`) do not terminate the header because they are
  at bracket depth > 0.
- **`.pyi` stubs** whose body is `...` on the header line still produce a valid
  span (start = header, end = end of that logical line).
- The suite-colon search is bounded by the next top-level statement. A **malformed
  header** with no suite colon before that boundary (e.g. `def broken()` with no
  `:`) is **skipped** — it is not emitted as a declaration and can never absorb
  the `:` of the following declaration.

| Python construct | `SourceDeclarationKind` | Exported? |
| --- | --- | --- |
| `def name(...)` / `async def name(...)` at column 0 | `function` | yes |
| `class Name(...)` at column 0 | `class` | yes |
| `def test_*` / `class Test*` at column 0 | `test` | no |
| names in `__all__ = [...]` | (contributes to `exports` only) | yes |

**Export convention:** if the file defines `__all__`, `exports` equals exactly
the `__all__` list. Otherwise `exports` equals every top-level `def`/`class` name
**not** starting with `_` (Python's public convention). `_private` names are
excluded. Static `__all__` parsing accepts list or tuple literals containing only
string literals, including parenthesized multi-line forms. If `__all__` is
dynamic or cannot be parsed completely, the analyzer falls back to the public
name convention; it must not emit a partial `__all__` result.

After the final export set is known, each non-test declaration receives
`exported: exports.includes(declaration.name)` and `search_names: [name]`. This
keeps compact compiler selection consistent with graph exports: a public
declaration omitted from static `__all__` is not marked exported, while a private
declaration explicitly listed in `__all__` is. A name exported through `__all__`
without a local declaration remains in `SourceAnalysis.exports` but creates no
fabricated declaration.

The scanner best-effort skips declarations/imports inside comments and
triple-quoted strings, including prefixed strings such as `r"""..."""`. It is
not a Python syntax validator: malformed or unterminated strings may suppress
later discoveries, but must not fabricate spans outside the source bounds. This
limitation is documented and covered by a deterministic malformed-input test.

**Worked example (must be covered by tests):**

```python
@app.get("/users")
async def list_users(
    limit: int = 10,
) -> list[User]:
    return users[:limit]
```

- `start` at `@app.get`, `end` after `return users[:limit]`.
- `signature` = `async def list_users(\n    limit: int = 10,\n) -> list[User]:`.
- `kind` = `function`, exported (no leading `_`), full body in the excerpt.

### Import grammar

Recorded as `ParsedImport` with `kind: 'static_import'`, `start`/`end` at the
import statement (or its parenthesized span). Semantics and required tests:

- `import a.b.c` → one import, specifier `a.b.c` (absolute).
- `import a, b` → two imports, specifiers `a` and `b`.
- `import a as b` → one import, specifier `a` (alias ignored for resolution).
- `from x import y` → specifier `x` (absolute).
- `from .x import y` → specifier `.x` (relative).
- `from ..a.b import c` → specifier `..a.b` (relative).
- `from . import x` → **module import**: normalized to specifier `.x` and
  resolved to the sibling module `x` (see below). It is not distinguished from
  `from .x import y` in this phase.
- `from . import x, y` → two imports (`.x`, `.y`).
- Parenthesized multi-line imports `from m import (\n a,\n b,\n)` → one import
  with specifier `m`, span covering the parenthesized block.

### Import resolution (`resolveImport` → `ImportResolution`)

**Relative** (specifier starts with `.`):

1. Count leading dots: 1 = importer's own directory; 2 = one package up; etc.
2. Map the remainder (`a.b`) to `a/b`.
3. **Named relative** (a remainder exists, e.g. `.x`, `..a.b`, or `from . import x`
   normalized to `.x`): candidate order, first present in `sourceFiles` wins —
   `<base>.py`, `<base>.pyi`, `<base>/__init__.py`, `<base>/__init__.pyi`. There is
   **no** current-package `__init__` fallback in this phase: a missing sibling is
   `unresolved_local`, never mis-resolved to the importing package's `__init__`
   (which would wrongly capture `from .missing import y`).
4. **Pure-dot** (no remainder, i.e. `.`/`..`): resolve the referenced package's
   own `__init__` — `<dir>/__init__.py`, `<dir>/__init__.pyi` (just `__init__.py`
   / `__init__.pyi` at the repository root; never a leading slash).
5. If the dot count walks above the repository root, return
   `{ status: 'unresolved_local' }` (it was clearly a local attempt).
6. Resolved → `{ status: 'resolved', path }`; otherwise
   `{ status: 'unresolved_local' }`.

**Absolute** (no leading dot), minimal repo-root resolution:

1. Map the dotted specifier `app.models` to `app/models` from the repository
   root.
2. Same candidate order: `<base>.py`, `<base>.pyi`, `<base>/__init__.py`,
   `<base>/__init__.pyi`.
3. Present in `sourceFiles` → `{ status: 'resolved', path }`.
4. Not found → `{ status: 'external' }` (third-party or stdlib; `src`-layout /
   `sys.path` deferred).

This keeps Django/FastAPI graphs edge-rich (`from app.models import User`
resolves) without a `sys.path` model.

## Graph wiring and enforcement activation

### Parser-driven import classification

`generateDependencyGraph` stops using the JS-style `specifier.startsWith('.')`
test. For each import reference:

```ts
const parser = parserForFile(file);
if (!parser) throw new Error(`no language parser for ${file}`); // inventory guarantees one
if (!reference.specifier) { unresolved: 'dynamic_expression'; continue; }
const result = parser.resolveImport(file, reference.specifier, { sourceFiles });
if (result.status === 'resolved') { edges.push({ from: file, to: result.path, kind: reference.kind, specifier }); }
else if (result.status === 'external') { unresolved: 'external_package'; }
else { unresolved: 'unresolved_local'; }
```

- `typescriptParser.resolveImport` returns `unresolved_local` for a `.`-prefixed
  specifier with no matching file, `external` for a bare package specifier, and
  `resolved` otherwise — reproducing today's behavior exactly.
- The existing `reason` set and `isDependencyGraph` are unchanged.

### Inventory safety

Add `.venv` and `__pycache__` to `IGNORED_DIRECTORIES`. Rationale: `.venv`
contains thousands of third-party `.py` files that must never enter the graph;
`__pycache__` holds only `.pyc` (not indexed) but is ignored for tidiness. Bare
`venv` is **not** added at the graph level — the name can legitimately be a
source package — and is left to the Phase 16.1 `python-api` profile policy
(`venv/`, `.venv/`). The fallback filesystem walker (used when `git ls-files`
fails) must apply the same ignore set; this path is explicitly tested.

### Compiler dispatch

Every `analyzeSource` call site in `context-compiler.ts` (compact excerpt
extraction and the three expansion paths — file, test, symbol) selects the parser
by path first:

```ts
const parser = parserForFile(pathOfSource);
if (!parser) throw new Error(`no language parser for ${pathOfSource}`);
const analysis = parser.analyze(content, pathOfSource);
```

- Python source therefore never reaches Babel.
- Excluded Python paths are already filtered out of the selection by Phase 16.1,
  so they never reach the analyzer at all (asserted by test).
- Add `py: 'python', pyi: 'python'` to `languageForPath` so Python excerpts get
  a fenced code block tagged `python` instead of an untagged fence.

### Phase 16.1 enforcement activation

Once Python files are graph nodes, `selectContextForObjective` traverses them and
`matchExclusion` (from 16.1) applies to `node.path`. `--expand-context` requests
for excluded `.py` files are rejected as `profile_excluded`. **No 16.1
exclusion-policy code changes** — it always matched on paths; there were simply
no Python nodes before.

Which rules actually bite (corrected wording):

- `migrations/` (django) and `alembic/versions/` (fastapi) take **direct effect**
  on `.py`/`.pyi` files that enter the graph.
- `.env` and `*.pyc` remain **forward / documentation policy** — those files are
  not indexed, so there is nothing in the graph to omit.
- `.venv`, `venv`, `__pycache__` are primarily **inventory-safety** concerns,
  handled by graph-level ignore (`.venv`, `__pycache__`) and profile policy
  (`venv`), not by omission of graph nodes.

### Refresh output

`runRefreshCodeGraph` prints a per-language breakdown when more than one language
is present: `N source files (M typescript, K python)`.

## Testing

Existing dependency-graph tests live in `test/context-routing.test.ts` (there is
no `test/dependency-graph.test.ts`). Plan: **new unit files** for the parser and
registry, and **extend `test/context-routing.test.ts`** for graph-integration and
the golden regression (its fixtures already live there).

### Unit — `test/python-analysis.test.ts` (new)

- Top-level `def`/`async def`/`class`; ignore indented (non-top-level) ones.
- **Declaration spans:** decorator-prefixed span starts at the decorator; `end`
  includes the full body up to the next top-level construct / EOF; trailing blank
  lines trimmed.
- Parenthesized multi-line decorators stay attached to the declaration span.
- **Multi-line signature** (the FastAPI worked example) captured whole; not
  truncated at the first `:`.
- **`.pyi` stub** `def f() -> int: ...` yields a valid span.
- Exports: with `__all__` → exact list; without → public names (no leading `_`);
  `_private` excluded; declaration-level `exported` flags agree with the final
  export set, including private names explicitly listed in `__all__`.
- Test detection: `def test_x` / `class TestY` → kind `test`, not in exports.
- Skip `def`/`class` inside `#` comments and prefixed/unprefixed triple-quoted
  strings; malformed input stays deterministic and all spans remain in bounds.
- Static multi-line list/tuple `__all__` is exact; dynamic/partial `__all__`
  falls back to public-name exports.
- Import grammar: `import a.b`, `import a, b`, `import a as b`, `from x import y`,
  `from .x import y`, `from ..a.b import c`, `from . import x`,
  `from . import x, y`, parenthesized multi-line import.

### Unit — `test/language-registry.test.ts` (new)

- `parserForFile('a.ts')` → typescript; `'a.py'`/`'a.pyi'` → python; `'a.md'`
  → null.
- `allExtensions()` = sorted union including `.py`/`.pyi`.
- **Registry collisions fail deterministically:** duplicate `id` throws;
  duplicate extension throws; non-`.`/non-lowercase extension throws.
- `pythonParser.resolveImport`:
  - relative `.x` → `pkg/x.py`, preferring `.py` over `__init__.py`;
  - `from . import x` (specifier `.x`) → sibling `pkg/x.py`, not `pkg/__init__.py`;
  - `..a` → one package up;
  - over-dotting past repo root → `unresolved_local`;
  - absolute `app.models` present at root → `resolved`;
  - absolute not found → `external`.

### Integration — `test/context-routing.test.ts` (extended)

- **Golden regression:** for a pure JS/TS fixture, normalize away `generated_at`
  (and `repository.revision`), ignore the additive `node.language` field, and
  assert `nodes`, `edges`, and `unresolved` match a checked-in golden expected
  output. `settings.extensions` is excluded from the comparison (it now includes
  `.py`/`.pyi`).
- **Polyglot graph:** Python node carries `language: 'python'`; a relative Python
  edge and a repo-root absolute Python edge both resolve; a genuinely external
  absolute import (e.g. `import os`) → `unresolved` reason `external_package`.
- `isDependencyGraph`: accepts a node missing `language`; rejects empty /
  non-string `language`.
- **Inventory:** `.d.ts` still excluded; `.venv` and `__pycache__` excluded; the
  fallback walker (git unavailable) applies the same ignore set.
- **No cross-language edges:** a `./foo` specifier in a `.ts` file does not
  resolve to `foo.py`.

### Integration — compiler/expansion end-to-end (extended compiler tests)

- Compile a Python file in **compact** mode → excerpt contains the full function
  body (not just the signature) and a fenced code block tagged `python`.
- Compile a Python file in **baseline** mode → whole file.
- **Expand** a Python file, a Python test, and a Python symbol.
- A **Django migration** `.py` is omitted in the compiled artifact
  (`omitted_context`); `--include-excluded "**/migrations/**"` brings it back
  into the excerpts.
- An **excluded Python file never reaches the analyzer** (asserted).
- **Legacy graph** lacking `language` still validates and compiles.

### Drift

No new drift test needed (the 16.1 exclusion table has its own drift test).

## Follow-up

Go (16.2b) and Rust (16.2c) analyzers register against the same contract and
`ImportResolution` result. Their module/workspace metadata may require additive
fields in `ImportResolutionContext`, but must not require new graph edge kinds or
language-specific switches in graph assembly. Python `src`-layout / `sys.path`
resolution, namespace packages, and AST-based parsing are later refinements that
do not change the graph schema.
