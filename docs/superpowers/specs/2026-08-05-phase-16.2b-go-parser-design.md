# Phase 16.2b — Go parser (design)

Date: 2026-08-05
Status: **proposed**
Target release: **3.11.0**

## Scope

This delivers the first of the two deferred language parsers from Phase 16.2
(Go now; Rust follows as 16.2c). It adds a **line-based `goParser`** registering
against the existing extension-keyed `LanguageParser` contract at the same depth
as the Python parser included in 3.11.0: declaration extraction with real
full-body spans, export detection, and intra-module import edges resolved through
the repository's `go.mod` module path. No new runtime dependency.

**In scope:**

- A line-based `goParser` (`bin/lib/go-analysis.ts`): brace-based declaration
  spans for `func` / method / `type` / `const` / `var`, including a contiguous
  leading doc-comment block; capitalization-based exports; `*_test.go` test
  detection; import parsing for single and grouped `import` forms.
- `go.mod` module-path import resolution: an import under the module path maps to
  a repo-relative package directory and resolves to **every non-test `.go` file**
  in that directory. Imports not under the module path are external.
- Registration of `goParser` in the production registry; `.go` in
  `allExtensions()`.
- Route the resolved-package edge fan-out through graph assembly by evolving the
  `ImportResolution.resolved` result to carry **multiple paths**.
- Add an additive `goModulePath` field to `ImportResolutionContext`, populated
  from the root `go.mod` by `generateDependencyGraph`.
- Graph-level ignore of `vendor` for inventory safety; Go Markdown fences in the
  context compiler; `node.language: 'go'`.

**Out of scope (deferred):**

- Rust parser (Phase 16.2c), which registers against the same contract.
- Multi-module repositories: nested `go.mod`, `go.work` workspaces, and vendored
  module resolution. Only the **root** `go.mod` module path is read — mirroring
  Python's repo-root-only absolute resolution. Files whose package is governed by
  a nested `go.mod` still parse, but their intra-module imports resolve against
  the root module path only.
- Build tags / build constraints, cgo, and generated-file heuristics beyond the
  existing exclusion policy.
- AST-based Go parsing (`go/parser`, tree-sitter, or equivalent). No new runtime
  dependency.
- Cross-package re-export lineage.

## Decisions

1. **`goParser` is line-based with real spans and no new dependency**, matching
   the Python precedent. Go is brace-delimited, so span boundaries use
   brace-depth tracking rather than Python's indentation model. String
   (interpreted, raw backtick), rune, and comment (`//`, `/* */`) state is
   tracked so keywords inside them are never mistaken for declarations or
   imports. It is not a Go syntax validator; malformed input stays deterministic
   and never fabricates spans outside the source bounds.
2. **Exports are capitalization-based.** Go's visibility rule is exact and
   local: a top-level identifier is exported iff its first letter is uppercase.
   There is no `__all__` analogue and no need to read other files. `_`-prefixed
   and lowercase names are unexported.
3. **A resolved Go import produces edges to every non-test `.go` file in the
   target package.** Go imports a *package* (a directory), not a file, and the
   dependency graph is file-keyed. The parser — the only component that knows Go
   resolves to a directory of files — owns the fan-out. This requires the
   `ImportResolution.resolved` result to carry `paths: readonly string[]`.
4. **Module resolution reads the root `go.mod`.** `generateDependencyGraph`
   extracts the `module <path>` directive from `<root>/go.mod` and passes it as
   `goModulePath` on `ImportResolutionContext`. An import equal to or under
   `goModulePath` maps to a repo-relative directory; anything else (stdlib,
   third-party, or absent `go.mod`) is `external`. This keeps intra-repo Go
   graphs edge-rich without a build-system model, exactly as Python's repo-root
   absolute resolution does.
5. **Doc comments are included in the declaration span.** A contiguous block of
   `//` line comments (or a single `/* */` block) immediately preceding a
   declaration with **no blank line** between the comment and the declaration is
   part of the span, because Go convention binds a doc comment to the symbol it
   precedes. This mirrors how the Python parser includes a declaration's
   decorators. `signature` still starts at the declaration keyword, not the
   comment.
6. **The graph schema stays `schema_version: 1`.** `node.language` (additive,
   introduced in 16.2) is set to `'go'`. Edge kinds stay
   `{static_import, dynamic_import, require}`; Go imports reuse `static_import`.
7. **The `ImportResolution` and `ImportResolutionContext` changes are additive
   and language-agnostic.** `typescriptParser` and `pythonParser` return
   `paths: [target]` (a one-element array) and ignore `goModulePath`; graph
   assembly loops over `paths`. Single-path languages therefore emit
   byte-identical edges, preserved by the golden JS/TS regression test.

## Architecture

```text
bin/lib/language-registry.ts   EDIT: ImportResolution.resolved -> paths: string[];
                                    ImportResolutionContext.goModulePath?: string;
                                    register goParser in the production registry
bin/lib/go-analysis.ts         NEW: goParser (line-based, brace spans, doc-comment
                                    inclusion, go.mod-driven resolveImport)
bin/lib/source-analysis.ts     EDIT: typescriptParser.resolveImport returns
                                    { status: 'resolved', paths: [target] }
bin/lib/python-analysis.ts     EDIT: pythonParser.resolveImport returns
                                    { status: 'resolved', paths: [target] }
bin/lib/dependency-graph.ts    EDIT: read root go.mod module path; pass
                                    goModulePath into resolveImport; loop over
                                    resolution.paths to emit edges; ignore 'vendor'
bin/lib/context-compiler.ts    EDIT: languageForPath gains go: 'go'
```

The parser modules stay free of process/manifest/filesystem access.
`dependency-graph.ts` remains the only filesystem/graph-assembly surface and is
where `go.mod` is read.

### LanguageParser contract changes

```ts
// language-registry.ts
export type ImportResolution =
  | { status: 'resolved'; paths: readonly string[] } // CHANGED: was `path: string`
  | { status: 'external' }
  | { status: 'unresolved_local' };

export type ImportResolutionContext = {
  sourceFiles: ReadonlySet<string>;  // all indexed files, repo-relative POSIX
  goModulePath?: string;             // NEW: root go.mod module path, e.g.
                                     // 'github.com/acme/svc'; absent if no go.mod
};
```

- `LanguageParser`, `LanguageParserRegistry`, `createLanguageRegistry`,
  `parserForFile`, and `allExtensions` are otherwise unchanged.
- Registry hygiene (duplicate id/extension fail-fast, extension format
  validation) is unchanged; `goParser` declares `id: 'go'`, `extensions: ['.go']`.

### Graph edge assembly (parser-driven, multi-path)

`generateDependencyGraph` reads the module path once, then the existing loop
(`dependency-graph.ts`) fans out over `resolution.paths`:

```ts
const goModulePath = readGoModulePath(repositoryRoot); // string | undefined
// ...
const resolution = parser.resolveImport(file, reference.specifier, { sourceFiles, goModulePath });
if (resolution.status === 'external')        { unresolved: 'external_package'; continue; }
if (resolution.status === 'unresolved_local'){ unresolved: 'unresolved_local'; continue; }
for (const to of resolution.paths) {
  const edgeKey = `${file}\0${to}\0${reference.kind}\0${reference.specifier}`;
  if (!edgeKeys.has(edgeKey)) { edgeKeys.add(edgeKey); edges.push({ from: file, to, kind: reference.kind, specifier: reference.specifier }); }
}
```

- The existing `edgeKey` dedup and edge sort are unchanged. A single-path
  resolution produces exactly one edge, identical to today.
- `resolution.paths` for Go is already sorted deterministically by the parser
  (see resolution below), so edge order stays stable.

### `readGoModulePath(repositoryRoot)`

- Reads `<repositoryRoot>/go.mod` if present; returns the argument of the first
  `module` directive (`module <path>`), trimmed. Ignores comments and the rest of
  the file.
- Returns `undefined` if `go.mod` is absent, unreadable, or has no `module`
  directive. With no module path, every Go import resolves `external` (no crash).

## Data model — graph schema

- `node.language = 'go'` (additive field from 16.2; `schema_version` stays `1`).
- `settings.extensions` reflects `allExtensions()` and now includes `.go`.
- `settings.ignored_directories` now includes `vendor`.
- `isDependencyGraph` is unchanged: it already accepts any trimmed non-empty
  `language` string and does not require a registered id.

**`go.mod` is included in the source fingerprint.** `buildSourceInventory` hashes
the content of `<root>/go.mod` (if present) into the fingerprint alongside source
files. A module path rename or the addition/removal of `go.mod` is therefore
detected as stale by `checkDependencyGraphHealth` without requiring any `.go` file
to change.

Compatibility: a repo containing `.go` files reports `stale` **once** after
upgrade (node count and fingerprint grow as Go files are indexed for the first
time); the `stale` message already instructs `--refresh-codegraph`. A repo that
has a root `go.mod` but **no** `.go` files will also report `stale` once (the
`go.mod` content now participates in the fingerprint). Repos with neither `.go`
files nor a `go.mod` are completely unaffected. Adding `vendor` to ignored
directories changes the inventory only for repos that previously indexed a
`vendor/` tree.

## Go parser semantics (`bin/lib/go-analysis.ts`)

Line-based scanning that tracks **brace, parenthesis, and bracket depth** together
with `//` and `/* */` comments, and interpreted (`"..."`), raw (`` `...` ``), and
rune (`'...'`) literals. A position is **top-level** only when all three depths are
0. This is necessary because multi-line function parameter lists have
`parenDepth > 0` on parameter lines, which must not be mistaken for top-level
boundaries. Returns the standard `SourceAnalysis` with JavaScript string offsets
(UTF-16 code-unit indices), matching the existing slicing contract.

**ASCII-only identifier parsing.** The Go spec allows Unicode uppercase letters as
exported identifiers, but the identifier regexes use `[A-Za-z_][A-Za-z0-9_]*` for
simplicity. Non-ASCII exported names (e.g. `func Écrire()`) are not indexed. This
is a best-effort limitation, not a correctness requirement for the phase.

**Extensions:** `.go`. A file whose name ends in `_test.go` is a test file: its
top-level declarations are emitted with `kind: 'test'` and are never exported and
never importable.

### Declarations, spans, and signatures

A top-level declaration is a `func`, `type`, `const`, or `var` statement where
all three depth counters are 0, optionally preceded by a contiguous
**doc-comment block** — one or more `//` line comments, or a `/* */` block
(single-line or multi-line), on the lines immediately above the declaration
keyword with **no intervening blank line**.

- **`start`** = UTF-16 offset of the first line of the contiguous doc-comment
  block if present; otherwise the declaration keyword line.
- **`end`** = UTF-16 offset just before the next top-level construct begins, with
  trailing blank lines trimmed; end-of-file if none follows. For brace-bodied
  declarations (`func`, `type struct`/`interface`) the closing brace at depth 0
  ends the body; the span runs to the next construct. The **full body is
  included** so the compiler's full-excerpt mode slices a complete
  function/type.
- **`signature`** = the header text from the declaration **keyword** (never the
  doc comment) through the opening `{` for brace-bodied declarations, or the full
  logical line for brace-less ones (`type Alias = X`, `const Pi = 3.14`,
  single-line `func f() int { return 1 }` → header through `{`). Preserves
  newlines for multi-line signatures. Braces/parens inside parameter lists or
  types do not terminate the header prematurely because depth is tracked.

| Go construct | `SourceDeclarationKind` | `search_names` | Exported? |
| --- | --- | --- | --- |
| `func Name(...) {...}` | `function` | `[Name]` | `Name` starts uppercase |
| `func (r T) Method(...) {...}` | `function` | `[Method, "T.Method"]` | `Method` starts uppercase |
| `type Name struct {...}` / `interface {...}` | `class` | `[Name]` | uppercase |
| `type Name <other>` / `type Name = X` (alias) | `type` | `[Name]` | uppercase |
| `const Name ...` / `var Name ...` (incl. grouped) | `variable` | `[Name, ...]` | uppercase (per name) |
| top-level in `*_test.go` (e.g. `func TestX`) | `test` | `[Name]` | no |

- **Method receiver.** `func (r *T) Method()` and `func (r T) Method()` both
  yield declaration name `Method` with `search_names: ['Method', 'T.Method']`
  (pointer star stripped from the receiver type). The method is exported iff
  `Method` is uppercase, independent of `T`. Generic receivers
  (`func (c *Cache[K]) Get(key K)`) are supported: the `[K]` type-argument
  suffix is stripped before extracting the receiver type name.
- **Generic types.** `type Cache[K comparable] struct{}` yields `kind='class'`,
  `name='Cache'`. The parser skips the `[...]` type-parameter list after the
  declared name before testing whether the remainder starts with `struct` or
  `interface`. A `{` that appears inside a type constraint
  (e.g. `[T interface{comparable}]`) is never mistaken for the body opener.
- **Grouped declarations.** `const (\n A = 1\n B = 2\n)` and the equivalent `var`
  / `type` groups yield **one** declaration span covering the whole group, with
  `search_names` listing every declared name in the group and `name` set to the
  first. Each name contributes to `exports` independently by its own
  capitalization.
- **`exports`** = every top-level declared identifier that starts with an
  ASCII uppercase letter (`[A-Z]`), sorted and de-duplicated. (The Go spec
  uses Unicode uppercase, but the parser's identifier regex is ASCII-only for
  this phase — see the ASCII limitation note in the parser semantics section.)
  Test-file declarations are excluded. After the export set is known, each
  non-test declaration receives `exported: exports.includes(name)` for its own
  name (grouped members are reflected via `search_names` in the graph's export
  list).

The scanner best-effort skips `func`/`type`/`const`/`var`/`import` keywords that
appear inside comments or string/rune literals, including raw backtick strings
spanning multiple lines. Malformed or unterminated literals may suppress later
discoveries but must not fabricate spans outside the source bounds. This is
covered by a deterministic malformed-input test.

**Worked example (must be covered by tests):**

```go
// ListUsers returns the first `limit` users.
// It never returns nil.
func ListUsers(
	ctx context.Context,
	limit int,
) ([]User, error) {
	return users[:limit], nil
}
```

- `start` at the `// ListUsers ...` comment line, `end` after `}`.
- `signature` = `func ListUsers(\n\tctx context.Context,\n\tlimit int,\n) ([]User, error) {`
  (from the `func` keyword, doc comment excluded, through the opening brace).
- `kind` = `function`, exported (uppercase `ListUsers`), full body in the excerpt.

### Import grammar

Recorded as `ParsedImport` with `kind: 'static_import'`, `start`/`end` at the
import statement (single line) or covering each spec line within a block:

- `import "fmt"` → one import, specifier `fmt`.
- `import ( "fmt"\n "net/http" )` block → two imports, specifiers `fmt` and
  `net/http`; each import's span covers its own line.
- Aliased / dot / blank forms — `import f "mymod/foo"`, `import . "mymod/foo"`,
  `import _ "mymod/foo"` — yield specifier `mymod/foo` (the import **path**);
  the alias, `.`, and `_` are stripped and ignored for resolution.
- Import paths are the quoted string; interpreted-string escapes are not expected
  in import paths and are taken literally.

### Import resolution (`resolveImport` → `ImportResolution`)

Go has no relative (`.`-prefixed) imports; every import is an absolute import
path. Resolution is module-path based:

1. If `goModulePath` is absent → `{ status: 'external' }` (nothing intra-repo can
   be proven).
2. If the specifier equals `goModulePath` → the module root directory (`''`).
   If it starts with `goModulePath + '/'` → strip that prefix to get a
   repo-relative package **directory**. Otherwise (stdlib like `fmt`, or a
   third-party path) → `{ status: 'external' }`.
3. For the resolved directory `dir`, collect every entry in `sourceFiles` that is
   a **direct child** `.go` file of `dir` (i.e. `dir === parentDir(file)`),
   **excluding** any `*_test.go` file. Sort the collected paths lexicographically.
4. Non-empty collection → `{ status: 'resolved', paths }`.
   Empty collection (the directory is under the module but contains no importable
   `.go` files in the index — absent, test-only, or excluded) →
   `{ status: 'unresolved_local' }`.

This keeps intra-module Go graphs edge-rich (`import "github.com/acme/svc/store"`
resolves to every `store/*.go` non-test file) without a build-system or
`GOPATH`/vendor model.

## Graph wiring and inventory

### Inventory safety

Add `vendor` to `IGNORED_DIRECTORIES`. Rationale: a Go `vendor/` tree contains
copies of third-party module source that must never enter the graph as
first-party nodes. The fallback filesystem walker (used when `git ls-files`
fails) applies the same ignore set; this path is explicitly tested. `.git`,
`node_modules`, `.venv`, `__pycache__`, etc. remain as-is.

### Compiler dispatch and fences

- `context-compiler.ts` already selects the parser via `parserForFile` at every
  `analyze` call site (added in 16.2). Go source flows through unchanged and
  never reaches Babel.
- Add `go: 'go'` to `languageForPath` so Go excerpts render inside a fenced code
  block tagged `go` instead of an untagged fence.
- Phase 16.1 exclusion enforcement applies to `.go` nodes automatically once they
  exist in the graph (no exclusion-policy code change). Excluded Go paths are
  filtered out of selection before reaching the analyzer.

### Refresh output

The existing per-language breakdown in `runRefreshCodeGraph` picks up Go
automatically: `N source files (M typescript, K python, J go)` when more than one
language is present.

## Preserved behavior (must not change)

- `.d.ts` files remain excluded from indexing.
- `typescriptParser` and `pythonParser` resolve exactly as before; only the
  result shape changes to `paths: [target]`. The golden JS/TS regression test
  enforces structurally identical nodes, edges, and unresolved entries.
- No cross-language edges: the Go resolver only ever collects `.go` files, and
  TS/Python resolvers only their own extensions, so a shared `sourceFiles`
  containing multiple languages never produces a cross-language edge.

## Testing

Mirror the Python parser's layout: a new unit file for the Go analyzer, an
extension of the registry unit tests, and extensions to the graph-integration and
compiler tests in their existing files.

### Unit — `test/go-analysis.test.ts` (new)

- Top-level `func` / `type` (struct, interface, alias) / `const` / `var`; ignore
  non-top-level (nested, brace-depth > 0) declarations.
- **Doc-comment inclusion:** a contiguous `//` block immediately above a
  declaration is part of the span (`start` at the comment); a blank line between
  the comment and the declaration excludes it; a `/* */` doc block is included.
- **Method receivers:** `func (r T) M()` and `func (r *T) M()` → name `M`,
  `search_names` `['M', 'T.M']`, exported by `M`'s case.
- **Grouped `const`/`var`:** one span, all names in `search_names`, per-name
  export by capitalization.
- **Spans:** `end` includes the full body to the next top-level construct / EOF;
  trailing blank lines trimmed.
- **Signature:** from the keyword through the opening `{`; multi-line signature
  (the worked example) captured whole; doc comment excluded from the signature.
- **Exports:** exact set of uppercase-initial top-level names, sorted/de-duped;
  lowercase and `_`-prefixed excluded; declaration-level `exported` flags agree.
- **Test files:** declarations in a `*_test.go` fixture → kind `test`, not in
  exports.
- **Comment/string safety:** `func`/`type`/`import` keywords inside `//`,
  `/* */`, interpreted strings, and multi-line raw backtick strings are skipped;
  malformed input stays deterministic and in bounds.
- **Import grammar:** `import "fmt"`; grouped block with two paths; aliased /
  dot / blank imports resolve to the import path with the qualifier stripped.

### Unit — `test/language-registry.test.ts` (extended)

- `parserForFile('a.go')` → go; `allExtensions()` = sorted union including `.go`.
- `goParser.resolveImport`:
  - module-prefixed import (`<module>/store`) → `resolved` with **all** non-test
    `.go` files in `store/`, sorted, `*_test.go` excluded;
  - import equal to the module path → the module-root package files;
  - stdlib / third-party path → `external`;
  - absent `goModulePath` → `external`;
  - module-prefixed dir with no importable files in the index →
    `unresolved_local`.
- TS/Python `resolveImport` now return `paths` arrays of length 1 (shape guard).

### Integration — `test/context-routing.test.ts` (extended)

- **Golden regression:** the existing pure JS/TS fixture still produces
  byte-identical `nodes`/`edges`/`unresolved` (after normalizing `generated_at`,
  `repository.revision`, ignoring additive `node.language`, and excluding
  `settings.extensions`) despite the `paths` contract change.
- **Polyglot graph:** a Go node carries `language: 'go'`; an intra-module import
  fans out to **every** non-test `.go` file in the target package (multiple
  edges); a stdlib import (`import "fmt"`) → `unresolved` reason
  `external_package`.
- **Inventory:** `vendor/` excluded under both `git ls-files` and the fallback
  walker; `.d.ts` still excluded.
- **No cross-language edges:** a Go import path never resolves to a `.ts`/`.py`
  file, and vice versa.
- `readGoModulePath`: repo with no `go.mod` → Go imports all `external`, no
  crash; `go.mod` with a `module` directive → module path picked up.

### Integration — compiler/expansion (extended compiler tests)

- Compile a Go file in **compact** mode → excerpt contains the full function
  body (not just the signature) inside a fence tagged `go`.
- Compile a Go file in **baseline** mode → whole file.
- **Expand** a Go file, a Go test, and a Go symbol (function/type).
- **Legacy graph** lacking `language` still validates and compiles (unchanged).

### Drift

No new drift test needed (the 16.1 exclusion table has its own drift test; no
exclusion-table change here).
